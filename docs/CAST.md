## 一、自动裁切：你那个思路的评估

### 结论：判据完全成立，但**不能"逐步放大 + 反复重测"**，要一次算到位

你的判据翻译成几何语言是：

> 放大到「两条中轴线只剩一条两端还有黑的」= 内容在**某一个方向上刚好贴满屏幕**，另一个方向留边。

这正是 `min(屏宽/内容宽, 屏高/内容高)` 这个缩放系数 —— 一次性就能算出来，而且**收敛点就是它**。

为什么不能真的"放大一点、再测一次、不够再放大"：

**探测读的是解码器输出的原始码流帧，放大裁切改的是本机显示。两者不在同一个域。**
原始帧里那两条黑边永远在那里，你把画面放大到天上去，`BorderProbe` 量到的还是原来的比例
⇒ 循环永远不满足退出条件，只会一直放大到内容被切光。

想让"逐步放大"能收敛，就必须去测**本机合成后的画面**——那是 v1.2.9 走过的路（`PixelCopy` 抓
SurfaceView），结果就是反馈回路：放大后黑边被推出可视区，从此永远测不到，手机换了画面本机还卡在
裁切状态。所以这个方向是死路，已经写进代码注释防止再走。

### 真正的病灶在旧版的缩放公式

旧版是 `max(屏宽/内容宽, 屏高/内容高)` —— 为了"铺满"而把内容**再切掉一截**。
竖屏手机投到 1920×1200 上时，内容被放大到 1920×1929，上下各切掉 364px，
看起来就是"裁得过头、手机屏幕被吃掉一块"。

改成 `min()` 之后：内容完整保留，竖向正好贴满，左右留边（这是竖屏手机在横屏上的必然结果，物理上
消不掉）。另外补了 `translationX/Y`：黑边左右不对称时，把内容挪回屏幕正中（旧版只改尺寸不挪位置，
不对称时会偏）。

### 探测算法按你的思路重写了（`BorderProbe.kt`）

| | 旧 | 新 |
|---|---|---|
| 采样 | 整行/整列全黑扫描，O(W×H)，每秒几十万次读 | **只看横/竖两条中轴线**，O(W/3+H/3) |
| 判据 | 整行全黑 | 两端连续黑游程 + 四道闸 |
| 频率 | 每秒 1 次 | 每秒 1 次（成本低了两个数量级，可再提） |

四道闸（专治"两端黑"的马后炮误判）：

1. **平坦性**——黑区亮度 max−min ≤ 14。黑边是死黑无纹理，夜景暗部有噪点，过不了；
2. **中段亮度**——内容区平均亮度 ≥ 30，全黑/黑场直接判"这一帧不算"；
3. **垂直校验**——横轴量到的左黑边，要在 1/4、3/4 高度处也是黑的才算"边"，
   否则只是某个黑物体恰好横在中轴线上；
4. **面积下限**——内容区每一轴 ≥ 18%。

外加"维持一小段时间"：连续 2 次采样一致才采纳（约 2 秒），转场/黑帧不会打抖。

### 顺手修掉的一个真 bug：探测"饿死"在等 IDR

影子解码器原来"解出一帧立刻停"，下次请求要重新等一个 IDR。手机端 IDR 不密时，
量到的常常是好几秒前那一帧 ⇒ 手机换了画面本机迟迟不动，体感就是"自动裁切又慢又迟钝"。
现在改成**小区喂帧**（`PROBE_BURST_FRAMES = 6`，≈0.2 秒），`acquireLatestImage` 拿到的永远是最新帧，
解码开销仍只有满负荷的 1/5。

## 三、投屏菜单改版

点屏幕 → **左侧投屏菜单 + 右侧投屏信息**，中间留出画面。

**左侧菜单**（镜像）：画面模式（适应/铺满/16:9/拉伸/自动裁切）、系统导航栏、
反向控制开关、**反控格式**（新增，见第四节）、关闭菜单。
**左侧菜单**（DLNA）：画质、播放速度、屏幕方向、视频信息、关闭菜单。

**右侧信息**（镜像 14 行）：类型、编码、**解码（硬解/软解 + 解码器名）**、画面流、内容区、
显示、帧率、码率、延迟、丢包、Wi-Fi 频段/信道、链路速率、实际吞吐、自动裁切量。
**右侧信息**（DLNA 10 行）：类型、编码、解码、分辨率、码率、帧率、预缓冲、网速、Wi-Fi、链路速率。

实现要点：

- **DLNA 不让菜单挡住播放控制条**：菜单顶部让开 64dp 状态条，底部预留 116dp 给控制条；
  两者联动 —— 菜单打开时把控制条一起叫出来并把自动隐藏放宽到 15 秒，控制条自己收起时菜单跟着收；
- 画面区域的点击**由 Activity 接管**（否则会和 PlayerView 各切一次，出现"点一下画面，
  控制条关了菜单还开着"）；落在底部 132dp 控制条带上的触摸原样放行，进度条拖拽/按钮不受影响；
- 面板本身 `clickable=true`，点空白处不会误触发"收起画面"。

## 四、反控（UIBC）与小米相册：怎么配合才能一次修好

### 4.1 UIBC：现在的真实状态

- 协商通了，**单击/双击/长按在手机上有效**（v1.2.17 实测）
- **滑动无效**，落点也偏
- 根因：**手机从不回 `wfd_uibc_capability`**，它按自己认定的输入类别解析我们的包。
  我们按 Mouse 发（type 0/1/2 + `btn+x+y`）能点，说明它确实按 Mouse 解析；
  但 Mouse 语义里没有"触摸拖动" —— 列表滚动在 Android 上靠触摸手势，鼠标拖拽是不滚的。

要定位到底该发什么，只看现象没法判断，必须**换格式试**。所以 v1.2.18 加了格式切换
（`UibcBridge.profile`，持久化，菜单「反控格式」即时切换，不必重连）：

| profile | 格式 | 说明 |
|---|---|---|
| 0（默认） | Mouse 5 字节 `btn+x+y`，type 0/1/2 | 现状，能点 |
| 1 | Mouse 规范格式：按下/抬起 **payload 长度 0**，移动 4 字节 `x+y`；按下前自动补一个 MOVE 定位 | 猜现在是"多给了字节导致移动被解析成垃圾坐标" |
| 2 | Touch：type **4/5/6**，payload `触点数+指针id+x+y` | 若手机其实支持触摸，这套才能滑 |

**你需要做的（3 分钟，一轮就能定性）**：

1. 手机投屏到本机；
2. 大屏上点一下 → 菜单出来 → 点「反控格式」切到一档 → 点「关闭菜单」；
3. 在大屏上：**点一个图标**（看落点准不准）→ **按住往上滑一次**（看列表滚不滚）；
4. 三档各试一遍，告诉我「哪一档点得中、哪一档能滑」。

如果三档都滑不动，那就是手机端只实现了 Mouse 语义 —— 这个功能对这台手机就到头了，
只能在手机上操作（或者换支持 UIBC 触摸的 Source，比如部分 Windows 机器）。

### 4.2 小米相册"设备已在投屏状态"

现状理解：手机能看到本机，但判定"已经在投屏"因而拒绝发起。

可疑点：**本机是"常驻自主 GO"**（`WifiDirectManager` 开机就 `createGroup`，为了能挂 WFD IE 被扫到）。
对端扫到的这个 P2P 设备状态可能是 `CONNECTED`（已经在组里），MIUI 就把"已在投屏"这个标签贴上去了。

**你要配合做的（一轮取证，按顺序）**：

1. 打开小米相册投屏，**先别点**，记下列表里本机的显示状态（正常名称 / 灰的 / 带"投屏中"字样）；
2. 点它，等到出问题，**立刻**（别重启 App）在电脑上跑：
   ```
   bash _工具/cast_diag.sh collect
   ```
   会生成 `_日志/cast_diag_<时间>.txt`，里面有 `dumpsys wifip2p`（组状态 + 对端列表）、
   接口状态、以及本 App 的全部日志。**把那个文件发给我**；
3. 再做一个对照：App 里把「接收投屏」关掉（会 `removeGroup`），再看相册列表里本机还在不在、
   状态变了没有，告诉我结果。

拿到这两组数据就能判定是"MIUI 按 P2P 状态过滤"还是"协议层拒绝"，然后才谈改法
（可选方向：不预建组、建组后立即改成 `AVAILABLE` 语义、或者干脆给小米走 DLNA 通道）。

## 七、复盘：v1.2.18「自动裁切没生效」的三个真因（v1.2.19 已修）

2026-10-26 17:00 用户实测 B 站投屏：画面四周都有黑边、完全没放大。抓日志：

```
Mirror scale(4 crop=0.000,0.073,0.000,0.035) video=1920x1080 parent=1920x1200
```

真值（从截图量）是 L=R=9.9%、T=9.9%、B=5.8%，**左右居然量成 0**，上下也各少了 ~2.5%。
三条独立的原因叠在一起：

### ① 探测缓冲尺寸写死 640×360（主因）
`ImageReader.newInstance(640, 360, ...)` 而画面流是 1920×1080。解码器会把整帧塞进这个
640×360 的缓冲，边缘再叠上它自己的对齐/缩放处理，量出来的比例整体失真。
**修**：`acquireSurface(videoW, videoH)` ——按视频真实尺寸建（>1920 才按整数倍缩小，
保证比例 1:1）。

### ② 只看一条中轴线，会被画面里的暗部骗
B 站这帧画面**左边本来就是一片接近纯黑的帘子**（亮度 0~10，跨 8% 宽度）。只看中线，
它是"黑边"，量出 17.7%，真值 9.9% —— 会把真实画面裁掉。
**修**：每条边量 **5 条线（10/30/50/70/90%）取最小值**。真黑边在 5 条线上一样宽，
最小值正好还原真值；画面暗部只污染个别线。

### ③ 单点判黑，被解码器边缘振铃杀掉整条黑边
解码器输出的画面最外圈常有 1~2px 亮点/噪点，单点判就直接"到边界了"，整条黑边变 0。
**修**：判黑改成**三点平均**（当前点 + 前后各一）。

### 验证方法：离线跑真图
`_工具/_probe_offline_test.py` 把真机截图合成成"1920×1080 的码流帧"，再用 Kotlin 同样的
判定逻辑跑一遍（含"加边缘亮点"的对照）：

| | L | R | T | B |
|---|---|---|---|---|
| 真值 | 9.90% | 9.90% | 9.91% | 5.83% |
| 量出 | 9.95% | 9.95% | 9.82% | 9.72% |

（B 偏大是因为合成时贴图边界带了几行暗像素，实际流里不会有）
按 `min()` 公式算出的最终结果：view=2397×1348，**内容可见 1920×1085 → 左右铺满、上下各留 58px**
—— 正是用户描述的目标状态。

> 结论：`min()` 判据没错（用户自己描述的"左右铺满、上下留点黑边"就是这个），
> 错的是**量黑边这一步**。以后任何"裁切不对"的问题，先看 `BorderProbe` 那行 `L=? R=? T=? B=?`。

## 八、换掉自研判据：改用电视/学术界的投影统计算法（v1.2.20）

用户要求重做，四条硬指标：① 裁完尽量大、不留黑边 ② 不裁掉有用信息（弹幕/一点 UI 可牺牲）
③ 反应快 ④ 别吃资源。

### 检索到的成熟做法

| 来源 | 关键点 |
|---|---|
| SCITEPRESS 2014《Automatic Letter/Pillarbox Detection for Optimized Display of Digital TV》 | 逐行算**黑像素占比**，≥80% 才算黑条行；只在中间 50%（0.25~0.75）取像素避台标；要求**连续 Nc=20 行都不黑**才认定黑边结束；宽高比要连续 Nf 帧稳定才生效 |
| onetask「Remove Black Bars」 | 取 10 帧，逐行记录**这几帧里最亮的像素**，只有始终是暗的才算黑条 ⇒ 黑场景/淡入淡出骗不过；工作分辨率压到 480 宽；阈值 Strict 16 / Normal 28 / Loose 40 |
| ffmpeg `cropdetect` | `limit` 默认 24、`round` 16、`reset` 用于黑边变化的素材 |

结论：**没有比"逐行/逐列黑像素占比 + 连续行确认 + 多帧一致性"更好的通用算法**。
所谓"AI 自动裁切"（CVPR 2008 的 Pan-Zoom-Scan）要训练、要算显著图，低端 SoC 上不现实。

### 落地实现（BorderProbe v3）

- 逐行/逐列统计黑像素占比（`≥92%` 才算黑条行/列）；只在中间 70% 取像素避台标；
- 必须**连续 6 行都不是黑条**才算黑边结束（黑边里混一行字幕不会提前结束）；
- 判黑用**三点平均**（防解码器边缘振铃）；
- 探测缓冲**按视频真实尺寸建**（≤960，整数倍缩小），分析在 1/2 分辨率上隔点采样
  ⇒ 一次约十几万次读，4Hz 跑占总 CPU 不到 1%；
- 请求频率 250ms、每次只喂 2 帧给影子解码器（≈满负荷 1/4）；连续 2 次一致即采纳 ⇒ **反应 ≈0.5 秒**。

### 缩放判据：铺满但不乱切（新增「裁切力度」三档）

去掉黑边后算两个缩放系数：`sFit`（只去黑边，一点内容不切）、`sCover`（铺满，溢出轴会被切掉）。
需要切掉的比例 ≤ 力度上限就用 `sCover`（**0 黑边**），否则退回 `sFit`（宁可留边也不切内容）。

| 档位 | 上限 | 适用 |
|---|---|---|
| 保守 | 0 | 一点内容都不切，铺不满就留边 |
| **标准（默认）** | 12% | 16:9 / 1.85:1 内容正好铺满，一条黑边都不留 |
| 激进 | 25% | 2:1 也能铺满，代价是画面边缘 |

### 四道防误裁的闸

1. 行/列黑像素占比 ≥92%（画面里的暗部占不满一整行 —— 这正是"单条中线"方案翻车的地方）；
2. 单侧黑边 >18% 直接判为"画面内容"不裁（真 padding 顶天 15%，竖屏手机的 37% 本来也不该裁）；
3. 边界必须是**跳变**（黑边→内容亮度差 ≥22），渐变说明是暗部；
4. 内容区面积 ≥22%、平均亮度 ≥24，否则这一帧判不了、保持原状。

### 离线验证（`_工具/_probe_v3_offline_test.py`，用的就是真机那张截图）

| 场景 | 结果 |
|---|---|
| A 正常黑边（B站真图） | L/R=9.95%、T=9.91%、B=9.81%（真值 9.90/9.90/9.91/5.83）→ 铺满，0 黑边 ✓ |
| B 左侧 31% 纯黑暗部 | 单侧上限拦下，L=0 → 保留黑边，不切内容 ✓ |
| B2 左侧 10% 纯黑暗部 | 同样被拦（保守）✓ |
| C 黑边里混一行字幕 | 仍能铺满，字幕被顺带裁掉（用户明确说弹幕无所谓）✓ |
| D 全黑帧 | 判定"判不了"，保持原状 ✓ |

菜单打开时那点 1 秒一次的文本刷新只更新信息面板的文字，不碰画面。

### 新增的挡位

菜单「画面模式」= 适应 时，多出两行：

- **左右裁切**：0 / 5 / 10 / 15 / 20 / 25 / 30 / **33 / 35 / 37** / 40 %
- **上下裁切**：0 / 3 / 5 / 8 / 10 / 12 / 15 / 20 %

点开是单选列表，选完立刻生效并持久化，下次会话沿用。

33/35/37 是专门留给竖屏手机的：9:20 的手机塞进 16:9 流，左右各空
`(1 - 0.45/1.778) / 2 ≈ 37%`，9:16 的约 34%。以前 5% 步进只能选 35 或 40
（前者留条残边、后者切一点画面），所以中间补细。

### 缩放算法（保持不变）

```
s = min(屏宽 / 内容宽, 屏高 / 内容高)
```

只去黑边、不额外切内容 —— 内容的一个方向贴满屏幕，另一个方向留边。
挡位裁过量时也不会出现"为了铺满再切一截"的问题。

### 用法

竖屏手机投屏（左右留白）→ 左右裁切选 **37%**；
横屏电影带上下黑边（2.35:1）→ 上下裁切选 **12%**；
16:9 全屏视频贴边 → 两个都选「关」。
